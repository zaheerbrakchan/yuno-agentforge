1. WHAT THE PROJECT DOES (ONE-PARAGRAPH SUMMARY)
================================================================================

Yuno AgentForge is a full-stack multi-agent orchestration platform. Users can
create AI agents, wire them into visual workflows (LangGraph), run conversations
through a web Monitor UI or Telegram, and watch every agent step (tool calls,
responses, token usage) stream live via WebSocket. The demo scenario is payment
customer support: a user asks why an order failed, three agents collaborate
(orchestrator → analyst with DB lookup → response writer), and the platform
returns a human-friendly answer. A second workflow handles general support
(payment methods, refunds, hours) without order lookup. Smart cross-workflow
handoff automatically routes users to the correct team when they pick the wrong
workflow or ask the wrong type of question.

Key design decisions:
- LangGraph chosen over CrewAI/AutoGen: explicit graphs map 1:1 to ReactFlow UI
- FastAPI: async-native, WebSocket support, OpenAPI auto-docs

- Channel-agnostic executor: same workflow logic for Monitor, API, and Telegram
- Shared log queue: all channels stream events to Monitor WebSocket panel

5. ALL AGENTS (SEEDED ON STARTUP)
================================================================================

PAYMENT WORKFLOW AGENTS
-----------------------
1. Orchestrator (role: orchestrator)
   - Classifies user intent, writes internal handoff to analyst
   - No tools
   - Handles greetings, order IDs, general requests

2. Payment Analyst (role: analyst)
   - Calls lookup_payment when order ID present
   - Calls get_retry_recommendation for failed payments
   - Tools: lookup_payment, get_retry_recommendation

3. Response Writer (role: responder)
   - Customer-facing voice; writes 1-3 sentence friendly reply
   - No tools; never mentions internal agents/tools

SUPPORT WORKFLOW AGENTS
-----------------------
4. Support Router (role: orchestrator)
   - Routes general support topics (methods, refunds, hours, regions)
   - Detects when user needs payment investigation team

5. General Support Agent (role: custom)
   - Customer-facing general support
   - Tools: list_supported_payment_methods, get_support_info

Users can create additional custom agents via the Agents page (any role, tools,
system prompt, model, max tokens, memory toggle).

6. TOOLS (LANGCHAIN TOOLS)
================================================================================

lookup_payment(order_id)
  - Queries SQLite Payment table by order ID
  - Forgiving ID parsing: "order 1001" → ORD-1001
  - Returns: status, reason, amount, currency, gateway OR not_found

get_retry_recommendation(failure_reason)
  - Looks up PlaybookEntry table (DB-backed playbook)
  - Falls back to built-in defaults if no custom entry
  - Used after payment lookup for failed orders

list_supported_payment_methods()
  - Returns hardcoded list: Visa, Mastercard, Amex, PayPal, Stripe,
    PIX, OXXO, Mercado Pago, PSE, Nequi

get_support_info(topic)
  - Topics: hours, refunds, contact, regions
  - Hardcoded support policy text in backend/runtime/tools.py

All tools registered in backend/runtime/tools.py → AVAILABLE_TOOLS dict.

8. SMART CROSS-WORKFLOW HANDOFF
================================================================================

File: backend/runtime/handoff.py + backend/runtime/executor.py

When a user runs the WRONG workflow for their message, the platform auto-transfers:

Support workflow + payment/order question  →  Payment failure investigator
Payment workflow + general support question →  Customer support router

Intent classification (regex-based):
- payment_investigation: order IDs (ORD-1002), failure keywords
- general_support: payment methods, refunds, hours, regions, wallets
- greeting: hi, hello, thanks
- ambiguous: no handoff

Handoff behavior:
- Telegram / default API: single blocking run, chains both workflows
- Monitor UI (staged_handoff: true): phase 1 shows redirect message, pause,
  phase 2 runs target workflow; workflow dropdown auto-updates
- polish_handoff_message(): replaces internal router text with customer-facing redirect
- Same session_id preserved across handoff (full conversation thread)

API flags on POST /api/workflows/{id}/run:
  staged_handoff: true   — Monitor two-phase handoff UX
  skip_handoff: true     — Force run on selected workflow only

16. LOCAL DEVELOPMENT SETUP
================================================================================

Prerequisites:
  - Python 3.11+ (3.12 recommended)
  - Node.js 20+
  - OpenAI OR Anthropic API key
  - Optional: Telegram bot token from @BotFather

Steps:
  1. git clone https://github.com/zaheerbrakchan/yuno-agentforge.git
  2. cd yuno-agentforge
  3. cp backend/.env.example .env  (or create .env from section 15)
  4. Edit .env with your API keys

Run backend (from repo root):
  pip install -r backend/requirements.txt
  python -m uvicorn backend.main:app --reload --port 8000

Run frontend (separate terminal):
  cd frontend && npm install && npm run dev
  → http://localhost:5173

Docker alternative:
  docker compose up --build
  → Frontend http://localhost:3000, Backend http://localhost:8000

Run tests:
  python -m pytest backend/tests -v

IMPORTANT: Backend must run as `backend.main:app` from repo root (not from
backend/ folder) to avoid python-telegram-bot import shadowing by backend/telegram/

  - Backend sleeps after ~15 min inactivity (cold start ~30-60s)

Deploy steps:
  1. Connect GitHub repo to Render Blueprint
  2. Set secret env vars (OPENAI_API_KEY, TELEGRAM_BOT_TOKEN, etc.)
  3. Set VITE_API_URL on frontend = backend URL
  4. Deploy both services
  5. Verify /health and frontend pages
